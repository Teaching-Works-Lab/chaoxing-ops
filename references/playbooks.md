# 学习通任务剧本（思维链层）

> 与 `atomic-operations.md` 的分工（**先读这一段**）

|   |   |   |   |
| - | - | - | - |

> |       | 原子操作手册               | 本文件（任务剧本）                     |
> | ----- | -------------------- | ----------------------------- |
> | 回答的问题 | 这一步**怎么点才生效**        | 这类任务**先做什么、何时分支、什么算完成、失败往哪退** |
> | 粒度    | 单个动作，无状态             | 一串动作 + 状态，有事务边界               |
> | 索引方式  | 按控件/界面（A/B/C/D/G 编号） | 按任务目标（P1/P2/…）                |
> | 类比    | 词汇                   | 句式 / 语法                       |
>
> **原子是词汇，剧本是句式。** 只有词汇，每次都要现场重新推导顺序；而实测中代价最高的返工恰恰全部来自顺序、状态、回滚，不是来自「某个按钮点不动」。
>
> 查法：接到一个完整任务 → 先查本文件对应剧本；剧本里的 `[D7]` `[A3]` 之类标记是原子编号，执行到那一步再查原子手册。控件点不动 → 直接查原子手册。

## 剧本通用骨架（六段式，缺一段下次就会重踩）

每条剧本必须写全 6 段：

1. **目标与终态**：可观测的完成状态（不是"发布成功"这种自述，而是列表/计数/数据）。
2. **前置状态检查**：动手前先读现状 —— 判重、`pubstatus`、登录态、已有文件夹、题型计数基线。
3. **事务边界**：哪些步骤**必须放进同一次 nodejs 调用**，理由一律是 G1（调用结束页面重置）。这是本层最不可替代的信息。
4. **决策分支**：判据 → 分支，含 SKIP 条件与"不要误判为失败"的缓存/延迟情形。
5. **验证断言**：可机器判定的信号；页面跳转不算成功。
6. **失败回退与幂等**：半成品怎么清、续跑入口在哪、如何保证不重复创建。

末尾附**涉及的原子编号清单**。

## 记录原则

- 只沉淀「决策与顺序」，不复述原子里的点击方法，引用编号即可。
- 事故先归类：
  - 控件/浮层/确认框没生效 → **补原子**；
  - 顺序错了、状态丢了、分支判错、删了没清干净 → **补本文件的剧本或回退段**。
- 一次性业务数据（题号、具体班级号、时间戳）不写，除非作为格式示例。
- 教学业务决策（出什么题、覆盖哪些知识点、与已有题是否重复）**不属于本 Skill**，落在项目教学设计文档里（作业题目总表、不重复核对表）。本层只管「怎么把定好的东西安全落到平台」。

## 执行载体：思维链台账

剧本是「一类任务怎么想」，台账是「这一次任务想到哪了」。  
跨多次 nodejs 调用、批量、可能掉线、需要续跑的任务，动手前复制 `references/chain-template.md` 填好，把六段式实例化；逐步更新状态，任一验证断言失败即停并留下「续跑点」。一次性单步操作可只在回复里写出链，不必建台账。启动协议见 `SKILL.md`。

**「保持思维链」的实质**：调用之间页面会重置（G1），能跨调用携带的只有 **已完成清单 + 直连 URL + 台账**，不是页面状态、不是 ref、不是标签。P5 的续跑完全依赖台账第 7 段；没有台账，链在第一次调用结束时就已经断了。

## P1 批量把已有作业补发到另一个教学班（幂等续跑）

- **目标与终态**：目标班 `work/list` 出现全部目标作业标题，每班每人收到一份；两个班各自只有 1 条/题。
- **前置状态检查**：
  - 取两个班的 `clazzId`（注意「一个教学班含多个行政班」的情况，别按班名猜测）。
  - 从作业库列表读每份作业的 `workLibraryId`（`ul.dataBody_td[data]`）。
  - `goto` 发放设置页，读 `a.classData[data=clazzId]` 的 `pubstatus`：`'0'` 已发 / `'-1'` 未发。
- **事务边界**：**单份作业**的「goto setting → 发放对象 → 勾选 → 确认 → 发放 → 等"发布成功"」放在一次调用内。调用之间只保留一份「已完成清单」，不保留页面状态。
- **决策分支**：
  - `pubstatus === '0'` → **SKIP**，天然防重复、天然可续跑。
  - `'-1'` → 走发放。
  - 调用超时/SIGTERM → **不要整体重跑**：先 `goto` 列表读实际进度，与计划清单做差集，只补差集 `[D9]`。
  - 用主标签 `p1` 循环 goto，不用 popup 标签（会 `No target with given id found`）`[D10]`。
- **验证断言**：切每个班 `work/list?...&selectClassid=`，按标题计数 = 1；`Y未交` = 该班学生数；首次显示 `0 未交` 属统计延迟，`reload()` 一次后再判 `[D11]`。
- **失败回退**：出现 2 条 → 走 P4，不要直接重发。
- **原子编号**：D10、D4、D5、D6、D9、D11。

## P2 新建一份多题型综合作业并同时发给两个班（含真实事故回退）

> 这是「一次期末综合作业发布」的完整剧本，也是最能说明为什么需要本层的一条。

- **目标与终态**：一份作业含 5 类题型，题干中的 C 代码原样显示，题量/总分正确，两个班各 1 条。
- **前置状态检查**：
  - 业务侧先完成「与已有作业不重复」核对（不在本 Skill 内）。
  - 题库目标文件夹是否已存在；`reload()` 后读题型计数作为基线。
  - 作业列表按标题判重，避免重复创建。
- **事务边界（最关键，实测最大返工来源）**：  
  **「选题 → 从题库选题 → 进文件夹 → 等题目层三标志 → 勾选 → 完成选题 → 保存并发布」必须在同一次 nodejs 调用内闭环** `[D12]`。  
  跨调用（或中途换标签）会让编辑器重建为空白：`workid=` 变空、题量 0、标题回默认「新建作业<时间戳>」，选题结果全部丢失。  
  → 这不是任何单个原子的属性，是**整条链的事务边界**，只有剧本层能表达。
- **决策分支**：
  - 题干/选项含 `< > &` → 写 xls 前统一转义（`&`→`&amp;`→`<`/`>`），先 `&` 后其余；导入后断言 `#include <stdio.h>`、`n < MAXN`、`&&` 均正常且不含 `&lt;` 字面 `[D12]`。判据不成立就修数据重导，不要带病往下走。
  - 导入后题型下拉计数没变 → **先 `reload()` 再判**，缓存未刷新不是导入失败 `[D12]`。
  - 进文件夹后勾选前 → 必须等「题目层三标志」同时成立，固定 `waitForTimeout` 不可靠 `[D7]`。
  - 「保存并发布」DOM `a.click()` 无反应 → 改 snapshot 锚点 `@ref` 真实点击 `[D11]`。
  - 两个班：优先在首次发放设置里一次勾两个班；若已发一个班，剩下那个走 P1 的作业库直发，不要新建第二份作业。
  - 提交物是 URL / Gitee / GitHub 链接 / 网址 → 发布前必须检查「学生作答不允许粘贴答案」未勾选（该选项默认可能勾选）`[D15]`。
  - 点「发放」后不要凭 URL 加 `#` 或页面无反应就重试：先查 `pubstatus` / `work/list` 标题计数；重复调用 `publicWork()` 会新增已发布副本 `[D15]`。
  - 已发布作业要改设置 → 走「修改设置」页的「确定」，绝不再点「发放」`[D15]`。
- **验证断言**：编辑器「题量 / 总分」与清单一致；两班 `work/list` 各 1 条；`Y未交` = 班级人数（首次 `0` 先 reload）；题干显示断言通过。
- **失败回退（实测事故，务必记住顺序）**：  
  **在作业库删除作业，不会撤销已发放到班级的副本** → 学生会看到两条。
  1. 先按「作答时间」确认哪条是要删的旧副本（题量 0 / 时间更早）。
  2. 作业库删除该作业。
  3. **再到每个班**的 `work/list` hover 该行 → 点行内「删除」→ 确认。
  4. 每班验证只剩 1 条，之后才能重发。  
     → 只做第 2 步是最常见的半吊子回滚。
- **原子编号**：A2、A3、D7、D8、D11、D12、D10、D6。

## P3 主观题（简答 / 评析改错）作业从出题到发布

- **目标与终态**：题干、参考答案、解析三处 UEditor 内容正确；AI 批阅已开；两班各 1 条。
- **前置状态检查**：题目内容在业务侧定稿（参考答案里写清评分标准/得分点，AI 预批才准）；标题判重。
- **事务边界**：`UE.instants[*].setContent()` 与「保存并发布」在同一次调用内；**不要**用 `UE.getEditor()`（会重渲染导致写不进去）`[D11]`。
- **决策分支**：
  - 多题且要自定义分值 → 先切评分机制「自定义」再改 `input#score`，否则百分制会覆盖。
  - AI 批阅开关点 `a.useAi`（外层 `.kaiguan` 无效），以 class 出现 `ai-Dgblue` 为成功判据 `[D11]`。
  - HTML 里避免裸 `<` `>`，引用原文用 `<blockquote>`。
- **验证断言**：保存后跳到 `work/library/setting?...workLibraryId=新ID`；两班列表各 1 条；首次 `0 未交` reload 后为班级人数。
- **失败回退**：内容没写进去时**不要保存**，直接重开编辑器重填（未保存的半成品不入库，比事后删干净得多）。
- **原子编号**：D11、D4、D10、D6。

## P4 清理重复 / 半成品（回滚剧本）

- **触发信号**：同一标题在某班出现 2 条、或出现题量 0 的作业、或作业库删了但学生端仍可见。
- **顺序（不可颠倒）**：
  1. **先判定留哪条**：按作答时间、题量、班级标签，明确旧副本是哪一条。
  2. 作业库删除（只删库，**不**影响班级副本）。
  3. 逐班 `work/list` → hover 行 → 行内「删除」→ 确认。
  4. **每班验证只剩 1 条**，再考虑重建。
- **幂等**：删干净之前不重建；重建前再判重一次。
- **验证断言**：两班按标题计数均为 1，且未交人数恢复为班级人数。
- **原子编号**：D12（删除坑）、D6。

## P5 掉线 / 超时后的续跑（通用）

- **现象**：连续快速操作时登录态会被踢到登录页；一次 nodejs 调用超时被 SIGTERM，但**已提交的操作仍然保存成功** `[D9]`。
- **唯一正确动作**：`goto` 列表页读实际状态 → 与计划清单做**差集** → 只补差集。
- **禁止**：整体重跑、凭记忆判断「应该没成功」、不看列表就重建。
- **恢复依赖**：登录态失效需用户重新扫码（Agent 无凭据），此时把台账第 7 段「续跑点」（已完成清单 + 剩余差集）交给用户，恢复后按 P1 的 `pubstatus`/标题判重继续。
- **原子编号**：D9、D10、D6。

## P6 从课程名定位到「考试是线上还是线下 / 发布没发布」的判定（2026-11-25 新增）

- **目标与终态**：给出三个可观测结论——① 该课程下考试是否已发布（试卷库发放次数 + 考试列表是否有记录）；② 若已发布，考试属于线上还是线下；③ 状态（未开始/进行中/已结束）。结论必须附页面关键词/字段证据，不靠考试名称猜。
- **前置状态检查**：
  - 登录态有效；从个人空间按课程名定位 courseId / cpi（D13）。
  - 先分清用户说的「考试」是试卷库里的**卷子**，还是考试列表里的**已发布任务**（H1）；二者常被混用。
  - 注意复用掉线前的任务空间与已有标签页，先看 tabs 有没有停在发布页，别盲目新开空间。
- **事务边界**：`goto` 试卷库 → 读发放次数 → `goto` 考试列表 → 读状态 → `goto` 发放设置页 → 展开高级设置 → 打印关键词命中，放在**同一批调用**里完成；调用之间只带 courseId/cpi/paperid 和三个 URL，不带页面状态（G1）。
- **决策分支**：
  - 试卷库发放次数 = 0 **且**考试列表「暂无考试」→ 结论「试卷已入库、考试未发布」，线上/线下只能在**发放设置页**按 H2 判，不能因为没发布就说「查不到」。
  - 考试列表有记录 → 直接读状态筛选与考试码；若用户问线上/线下，仍走 H2 的发布设置页判据。
  - 页面出现「线下组织直播」**不要**判为线下考试（H2）；出现「考试码」也**不要**判为线下（线上考试也发放考试码）。
  - 跨调用页面重置 → 用 H1/H2 的直连 URL 重建，不依赖上一标签。
- **验证断言**：打印 `body.innerText` 长度与 `线上/线下/考试方式/考试码/考场/纸质` 命中数；断言无「考试方式」切换、无「纸质/考场」、且具备在线监考/切屏/手机 APP 等线上特征，才下「线上考试」结论。
- **失败回退**：登录失效 → `handOff()` 交用户扫码，凭台账里的 courseId/cpi/paperid 续跑；页面被重置 → goto 直连 URL 重来。判定证据不足时明确回答「平台未给出该字段」，禁止臆测。
- **原子编号**：D13、H1、H2、H3、H4。

## 附：实测事故归因表（为什么需要这一层）

| 发生过的现象                      | 属于哪一层     | 现在沉淀在                     | 若只有原子层           |
| --------------------------- | --------- | ------------------------- | ---------------- |
| 跨调用选题 → 编辑器空白、题量 0、标题回默认    | 流程 / 事务边界 | P2 事务边界（原子 D12 只能以「注意」附带） | 下次仍要现场推导顺序，且容易漏读 |
| 作业库删了作业，两班各留一条旧副本           | 流程 / 回滚   | P4（原子 D12 只有一句提醒）         | 学生看到两份，不知道要去班里删  |
| 首次进列表显示 `0 未交`              | 验证判据 / 分支 | P1、P3（原子 D11）             | 误判失败 → 重复发布      |
| 题型计数导入后不刷新                  | 分支判据      | P2（原子 D12）                | 误判导入失败 → 重复导入    |
| 一次调用超时但作业其实已发               | 幂等 / 续跑   | P5（原子 D9）                 | 整体重跑 → 产生重复      |
| 「保存并发布」DOM click 无效         | **控件原子**  | D11                       | **原子层已足够，无需剧本**  |
| UEditor 零尺寸、要 `UE.instants` | **控件原子**  | D11                       | **原子层已足够，无需剧本**  |

结论：**控件级问题原子层已经能覆盖；实测代价高的 5 个事故全是「链」的问题**。所以保留原子层作为底座，另加这一层剧本，而不是替换它。
